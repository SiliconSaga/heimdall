# Request right-sizing observations

The git-backed record behind design §6. Prometheus retains one week, so the numbers below are the only history that outlives the rolling window — this file is what turns a 7-day view into months of trend, diffable and reviewable, without the object-storage backend Thanos would need to answer roughly twenty numbers a week.

Generated by [`scripts/rightsize-report.sh`](../../scripts/rightsize-report.sh). Append a new section per run; never rewrite an old one, because the point is the drift between them.

```bash
# From the GDD workspace root, so calls route through the k8s guard.
# Paths are workspace-relative: `scripts/ws` is the workspace's, and the
# report script is inside this component.
KUBE_CMD="bash scripts/ws k8s" bash components/heimdall/scripts/rightsize-report.sh --window 7d --step 20m

# From a standalone heimdall checkout, where there is no workspace guard:
KUBE_CMD=kubectl bash scripts/rightsize-report.sh --window 7d --step 20m
```

**Tiers** (§6): *must-not-starve* — user-facing and control plane — targets ≈ p95; *idle controllers* sit at a 25–50m floor; **Jenkins is excluded** and hand-tuned by its owner, and the report filters its namespace out by default.

**The loop is mandatory, not optional.** CPU requests only bite under contention, so compressing one looks free and behaves identically right up until the hour the node is busy — Artifactory requested 50m for 605 days and then could not boot. Compression without a watch loop defers that outcome rather than avoiding it.

**Run it as a scheduled agent, not a CronJob**, at least to begin with. The valuable output is not the table but the judgment under it: which workload changed shape, whether a spike was real load or a neighbour's noise, what to adjust next. Graduate it to a CronJob only if that judgment ever becomes purely mechanical.

### Reading

**Artifactory is still configured the way it was when it took the site down.** Its CPU request remains **50m** against a 158m p95 and 235m max — the July hot-patch raised the *limit* to 750m and the startup-probe thresholds, but never the request. Memory is 1.2Gi over its request at p95. It leads the starve table and should lead the fix list. The durable change belongs in the Helm values the legacy ArgoCD app renders from, not another in-cluster patch.

**Heimdall's own Prometheus is under-requested on both axes** — 250m against a 327m p95, and 512Mi against 1061Mi. The observability stack is the last thing that should lose a contention race, since losing it is what makes every other problem invisible.

**`argocd-application-controller` carries the only OOM flag in the report**, with a 768Mi p95 against a 512Mi request and one restart. The July hot-patch on the new ArgoCD survived, but it was sized too small on memory. This is GitOps' own control loop.

**The three pgbouncers reserve 105m each and use a measured 0m** — 315m held for nothing across keycloak, harbor and ting. With `keycloak-operator` (300m for a 12m p95) that is over 600m, roughly a third of a node, reclaimable with no behavioural risk.

**`keycloak` is the one row that must not be read off p95 alone.** Its p95 is 6m but its max is 755m — a JVM warming up. Compressing it toward p95 would reproduce exactly the Artifactory failure: fine for months, then unable to cold-boot on a busy node. It is must-not-starve; size it for the spike, not the median.

**Throttling clusters on the seed Gitea stack and the Percona/CNPG postgres pods** (20–36%). Throttling is driven by *limits*, not requests, so it is a separate axis from the compression above — but it is worth noting the seed Gitea stack is simultaneously the largest block of reserved-and-idle CPU in the cluster *and* among the most throttled. That stack is the ephemeral Seed that the Forgejo day-2 arc retires, so the cheapest fix is to finish that arc rather than tune it.

**Caution — compression alone makes placement worse.** The cluster runs GKE's `optimize-utilization` profile, which bin-packs onto the fewest nodes. Trimming requests packs *tighter*, so reclaimed CPU does not spread load; it invites the scheduler to stack more onto the already-hottest node. Pair every compression with either the raised requests above (so the scheduler's model matches reality) or explicit spread constraints. On 2026-08-17 the four nodes sat at 90–99% requested and 30% / 42% / 62% / **102%** actually used — the scheduler had balanced the fiction almost perfectly and the reality not at all.
